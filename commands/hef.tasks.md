# Tasks

Generate a phased task list from the current branch's specification, and its plan when there is one.

## Pre-Flight

### Current branch
> The commands in this section must be run with the Bash tool; they cannot be
> pre-executed in a `!` block. A `!` block is permission-checked before the
> CLAUDE_PLUGIN_ROOT variable is substituted, so it is rejected as "Contains
> expansion". Do not write that variable with a $ and braces here: it would be
> substituted into this note and the warning would read as nonsense.

Run with the Bash tool: `${CLAUDE_PLUGIN_ROOT}/hooks/speckit-helper.sh branch`

### Which path: spec + plan (full) or spec alone (light)
Run with the Bash tool: `${CLAUDE_PLUGIN_ROOT}/hooks/speckit-helper.sh check-tasks-inputs`

### Load spec
Run with the Bash tool: `${CLAUDE_PLUGIN_ROOT}/hooks/speckit-helper.sh spec`

## Instructions

**Required inputs**: `spec.md` must exist for the current branch — on `NO_SPEC_FOR_BRANCH`, tell the user
to run `/hefesto:hef.spec` first. `plan.md` is optional: `FULL_PATH` means spec + plan, `LIGHT_PATH` means
the spec alone (the `/hefesto:hef.agent` Light route, which skips the plan). Never write or require a
`plan.md` on the light path.

1. **Load artifacts**:
   - Read `spec.md` for user scenarios (US#) and functional requirements (FR-NNN)
   - **Only if the pre-flight printed `FULL_PATH`**, run with the Bash tool:
     `${CLAUDE_PLUGIN_ROOT}/hooks/speckit-helper.sh plan` and read `plan.md` for affected files,
     implementation approach, and design decisions
   - On `LIGHT_PATH` never run the `plan` fetcher (it fails loudly with no plan, and that failure is not
     a stop on this path). Generate the tasks from the spec alone: target paths come from the files the
     spec names, else from a Grep/Glob of the code — and the summary says the paths were inferred without
     a plan. Write this line under the Date line of `tasks.md`:
     `<!-- Light path: generated from spec.md alone — no plan.md -->`

2. **Generate tasks in phases**:

   Write `.specify/specs/<branch>/tasks.md` (the `Light path` line is written on `LIGHT_PATH` only — omit
   it on `FULL_PATH`):

   ```markdown
   # Tasks: <branch-name>
   <!-- Generated by /hefesto:hef.tasks -->
   <!-- Date: YYYY-MM-DD -->
   <!-- Light path: generated from spec.md alone — no plan.md -->

   ## Phase 1: Setup
   - [ ] T001 [US1] <setup task description> `path/to/file`
   - [ ] T002 [US1] <setup task description> `path/to/file`

   ## Phase 2: Foundational
   - [ ] T003 [FR-001] <data model/schema task> `path/to/file`
   - [ ] T004 [P] [FR-002] <foundation task> `path/to/file`

   ## Phase 3: User Stories (by priority)
   ### P1 — Must Have
   - [ ] T005 [P] [US1] <implementation task> `path/to/file`
   - [ ] T006 [US1] <implementation task> `path/to/file`

   ### P2 — Should Have
   - [ ] T007 [US2] <implementation task> `path/to/file`

   ### P3 — Nice to Have
   - [ ] T008 [US3] <implementation task> `path/to/file`

   ## Phase 4: Polish
   - [ ] T009 [US1] <integration test> `path/to/file`
   - [ ] T010 <documentation/cleanup> `path/to/file`

   ---
   **Legend**: `[P]` = parallelizable | `[US#]` = user scenario | `[FR-NNN]` = functional requirement
   ```

3. **Task format rules**:
   - ID format: `T001`, `T002`, etc. (zero-padded 3 digits)
   - `[P]` marks tasks that can run in parallel with adjacent tasks
   - In a repository with several apps, a task that changes a file in **another** app than the one owning the spec
     names that path in the task line, so the reviewer sees the reach
   - A `[P]` task **declares what it owns**: `owns: path/a, path/b` after the target path — every
     file it will create or modify. Two `[P]` tasks in one phase may not own the same file; if
     they would, split by file or drop `[P]` from one. 42% of agent merge conflicts are add/add or
     modify/delete pairs, which is exactly what disjoint ownership prevents; the workflow batches
     by these lists and serializes any overlap it finds
   - Every task references at least one US# or FR-NNN
   - Every task includes a target file path
   - Tasks within a phase are ordered by dependency
   - A task that implements an FR must produce a test that **cites that FR id** (marker, describe
     title, or comment); `/hefesto:hef.verify` maps requirements to tests by that token, so a task whose
     test does not cite its FR leaves the requirement `UNCOVERED` no matter how good the code is

4. **Create TaskCreate entries** in the Claude Code task tracker:
   - One TaskCreate per task from the generated tasks.md
   - Subject: `[T001] <description>`
   - Description: include the user scenario reference, file path, and acceptance criteria from the spec
   - Set dependencies with TaskUpdate `addBlockedBy`/`addBlocks` where tasks have ordering requirements
   - Phase 1 tasks have no dependencies
   - Phase 2 tasks are blocked by Phase 1
   - Phase 3 tasks are blocked by Phase 2
   - Phase 4 tasks are blocked by Phase 3

5. **Present summary** to user:
   - Total task count by phase
   - Parallelizable task count
   - Estimated phases (sequential dependency chain length)
   - Suggest next step: `/hefesto:hef.implement` or `/hefesto:hef.checklist` for pre-implementation validation;
     after implementation, `/hefesto:hef.verify` closes the loop
